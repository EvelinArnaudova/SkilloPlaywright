API Test Flow how Playwright starts the server, signs in through the API, sends requests and cleans up

  • 1. webServer starts the API before any test
  • 2. request sends real HTTP: no browser
  • 3. Fixtures log in, build API clients and clean up
  • 4. UI tests reuse an API login through storageState
What is API testing? The basics in 2 minutes click or press I to show / hide

1. The idea in one sentence

An API test talks to the server directly over HTTP: it sends a request and checks the status, headers and JSON body. There is no browser and no HTML.

Analogy: instead of ordering in the restaurant (UI), you call the kitchen (API) directly.

2. Anatomy of an API test

test('GET posts', async ({ request }) => {
  const res = await request.get('/api/posts');
  expect(res.status()).toBe(200);   // 1. status
  const posts = await res.json();   // 2. body
  expect(posts.length).toBeGreaterThan(0);
});

5. What APIRequestContext gives you

APIRequestContext is Playwright's HTTP client. It runs in Node.js, not in a browser, so there is no page, no JavaScript and no CORS. Think of it as a scriptable Postman with a memory for cookies.

Three ways to get one:

  • { request }: the built-in fixture. Uses config options such as baseURL and extraHTTPHeaders; a fresh one per test, closed for you.
  • playwright.request.newContext({ ... }): your own context with its own settings (our authedRequest fixture). You must call dispose().
  • page.request: shares cookies with the browser. Log in here and the page is signed in too.
const res = await request.post('/api/posts', {
  data: { title: 'Hello' },                  // JSON body
  headers: { Authorization: `Bearer ${token}` },
});
expect(res.status()).toBe(201);
expect(res.headers()['location']).toMatch(/\/api\/posts\/\d+/);
const post = await res.json();

6. Why fixtures for API tests?

  • Login once per test, out of sight: apiToken + authedRequest.
  • Clients instead of URLs: postsApi.create(...), like a page object for the backend.
  • Automatic cleanup: posts deletes what the test created, even after a failure.
  • Same fixtures in UI tests: seed data through the API, check it in the browser.

7. The order of a full run

  • webServer (in the config, nothing else needed): reuse a running server, or run node server/server.mjs and wait until /api/health answers.
  • api project: api-tests/*.spec.ts, no browser.
  • setup project: auth.setup.ts logs in and writes .auth/qa.json.
  • ui-chrome / ui-firefox: wait for setup, then load the saved session.
  • After all projects: the runner stops the server it started.

8. Postman: explore the same API by hand

  • Not a Playwright feature: Playwright does not export or import Postman collections. postman/Lecture5-TeamBlog.postman_collection.json is a plain JSON file (Postman Collection v2.1) written for this lecture.
  • In Postman: Import → choose the file. Steps: POSTMAN.md.
  • From the terminal: npx newman run lectures/05-api-testing/postman/Lecture5-TeamBlog.postman_collection.json (Newman is Postman's CLI runner).
  • Start the server first (npm run start:api): webServer only works for playwright test.

Postman = explore and try by hand. Playwright = automated tests in the repo, with fixtures, cleanup and CI.

9. Watch out for

  • Only checking the status: a 200 with the wrong body is still a bug.
  • Leftover data: every created record needs cleanup, or the next run is different.
  • Hard-coded ids of data you created: read them from the response.
  • Logging in with the built-in request when other calls in the test must stay anonymous: it keeps the cookie.

Rule of thumb: set up through the API, check what matters where it matters.

API reference: every endpoint of the Team Blog API click or press A to show / hide

Base URL and format

  • http://localhost:3001: start it with npm run start:api (tests start it via webServer).
  • Requests and responses are JSON. Send Content-Type: application/json with a body.
  • Data is in memory: restarting the server resets it to the seed data.

Authentication

  • POST /api/login returns a token and sets a session cookie.
  • API clients: Authorization: Bearer <token>
  • Browsers: the cookie is sent automatically.
  • 🔒 auth = any signed-in user · 🔒 author = the post's author or an admin.

Test accounts and seed data

idemail / passwordrole
1admin@example.com / admin123admin
2dev@example.com / secret123qa

Posts 1 and 2 belong to the admin (2 is a draft), post 3 to QA. New posts get ids from 4.

Schemas

User     { id: number; name: string; email: string;
           role: 'admin' | 'qa' }
Post     { id: number; title: string; body: string;
           published: boolean; authorId: number }
ApiError { error: string; details?: string[] }

Same types in api/types.ts.

Errors: the server checks in this order

401who are you? (no or unknown token)
404does it exist? (also any unknown route)
403may you change it?
400is the body valid? (details lists every problem)

Get a token in the terminal

TOKEN=$(curl -s -X POST http://localhost:3001/api/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"dev@example.com","password":"secret123"}' \
  | node -pe 'JSON.parse(require("fs").readFileSync(0)).token')
echo $TOKEN

The curl examples below use $TOKEN. In Postman, the collection does this for you.

Auth

POST/api/loginSign in, get a tokenpublic

Returns a token for API clients and sets a session cookie for browsers. Each login creates a new session.

Request body · application/json

{
  "email": "dev@example.com",
  "password": "secret123"
}

Responses

200OK: signed in. Header: Set-Cookie: session=<token>; HttpOnly; Path=/
{
  "token": "3f2c9a1e-…",
  "user": {
    "id": 2,
    "name": "Dev QA",
    "email": "dev@example.com",
    "role": "qa"
  }
}
400Bad Request: email or password missing, or the body is not JSON
{
  "error": "email and password are required"
}
401Unauthorized: wrong email or password
{
  "error": "Invalid email or password"
}

Try it: curl

curl -X POST http://localhost:3001/api/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"dev@example.com","password":"secret123"}'

In a Playwright test

const response = await new AuthApiClient(request).login(users.qa);
const { token } = await response.json();
POST/api/logoutEnd the browser sessionpublic

Ends the session named in the session cookie and clears the cookie. The cookie value is the token, so that token stops working too. It ignores the Authorization header: sending only a Bearer token ends nothing (still 204).

Responses

204No Content: logged out (empty body)

Try it: curl

curl -X POST http://localhost:3001/api/logout -b "session=$TOKEN"

In a Playwright test

const response = await request.post('/api/logout');
expect(response.status()).toBe(204);
GET/api/meWho am I?🔒 auth

Returns the user behind the token or cookie. A quick way to check that auth works.

Responses

200OK: the signed-in user (never the password)
{
  "id": 2,
  "name": "Dev QA",
  "email": "dev@example.com",
  "role": "qa"
}
401Unauthorized: no token, or an unknown token
{
  "error": "Authentication required"
}

Try it: curl

curl http://localhost:3001/api/me -H "Authorization: Bearer $TOKEN"

In a Playwright test

const response = await new AuthApiClient(authedRequest).me();
expect(await response.json()).toMatchObject({ role: 'qa' });

POST/api/postsCreate a post🔒 auth

Only title is required. Defaults: body: "", published: false. The server sets id and authorId (the signed-in user); if you send them, they are ignored.

Request body · application/json

{
  "title": "My first post",
  "body": "Hello",
  "published": false
}

Responses

201Created: created. Header: Location: /api/posts/4
{
  "id": 4,
  "title": "My first post",
  "body": "Hello",
  "published": false,
  "authorId": 2
}
400Bad Request: invalid body
{
  "error": "Validation failed",
  "details": [
    "title must be a non-empty string"
  ]
}
401Unauthorized: no token
{
  "error": "Authentication required"
}

Try it: curl

curl -X POST http://localhost:3001/api/posts \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"title":"My first post"}'

In a Playwright test

const response = await postsApi.create({ title: 'My first post' });
expect(response.status()).toBe(201);
